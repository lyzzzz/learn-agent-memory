# 8 · 混合检索（Hybrid retrieval）

[English](README.md) · [繁體中文](README.zh-TW.md) · **简体中文**

> 一种检索方式很难覆盖所有问题。可以同时用几种成本较低的方法查找，再合并它们的排名。

这是[生产环境中的记忆系统](../../README.zh-CN.md)教程的第八章，负责从已有记忆中找出当前这一轮需要的信息。

“通道”（channel）就是一种查找候选结果的方法。向量相似度、关键词搜索、按最近时间排序，都可以作为独立通道。只用一种方法，总会有遗漏：向量检索不擅长精确名称、日期和否定表达；关键词搜索容易漏掉换了说法的同一件事；只看最近记录，又会错过年代较久但仍有用的信息。

问题本身也各不相同：“我们用哪家的 CI”在查名称，“上周决定了什么”在查时间，“以前部署出过什么问题”则需要找出共同情况。单一通道很难把这些问题都处理好。

基础记忆流程已经有两种查法：让大语言模型读取索引、挑选记忆，以及用关键词搜索原始历史。本章把它们扩展为一套统一流程：

1. 多个轻量检索通道并行运行。
2. 按排名合并结果，避免逐一调整通道之间的分数权重。
3. 某条通道出错时，其余通道仍能提供结果。
4. 区分“正常运行但没有命中”和“通道运行失败”。
5. 保持索引可重建：它是第 7 章所说的视图，可以从记忆记录重新生成。

## 实现机制

最小实现包含两个通道和一个排名融合函数：

- **检索通道：** 各自生成候选结果。离线版使用关键词搜索（FTS5、BM25）和最近优先。之后增加向量、图遍历或时间过滤时，也使用同一接口，返回排好序的 ID 列表。
- **排名融合：** 使用倒数排名融合（reciprocal rank fusion，RRF）。每个通道为命中的记录贡献 `1 / (K + 名次)` 的分数。
- **索引：** 从分类记忆生成的全文检索表，可以随时清空后重建。

RRF 让接入新通道比较简单。不同通道的原始分数通常不能直接比较，但可以按各自的名次累加贡献，因此不必先把分数换算到同一尺度，也不用调整通道权重：

```python
def fuse(channels, k=TOP_K) -> list[tuple]:
    scores, seen_in = {}, {}
    for name, ranking in channels.items():
        for rank, mid in enumerate(ranking):
            scores[mid] = scores.get(mid, 0.0) + 1 / (RRF_K + rank + 1)
            seen_in.setdefault(mid, []).append(name)
    best = sorted(scores, key=scores.get, reverse=True)[:k]
    return [(mid, scores[mid], tuple(seen_in[mid])) for mid in best]
```

一条记忆如果被多个通道找到，就会累加多个通道的得分，排序因此更倾向于这些共同命中的结果。不同检索信号都认为它相关，本身就是一条有用的依据。

两个通道读取同一张衍生索引表：

完整检索流程与本章实现的对应关系如下：

```text
理解查询                  生产实现：选择通道、扩展查询
    ↓
并行查找候选结果          关键词 · 最近优先；生产实现可加入向量、图、时间通道
    ↓
合并、去重、重新排序      使用 RRF 融合排名
    ↓
补充来源上下文            生产实现：读取命中事件的前后文，见第 2 章
    ↓
按 token 预算选取         由第 9 章负责
```

还有两种值得了解的方法，本章的离线版没有实现：

| | 补充来源上下文（Contextual expansion） | agent 自主检索（Agentic retrieval） |
| --- | --- | --- |
| **做法** | 命中一条记忆后，回到第 2 章的事件日志，读取相关事件的前后文。 | 把执行过程存成文件，让编程 agent 在沙箱里自行搜索。 |
| **研究结果** | MemMachine 发现，增加检索深度、展开来源上下文，常常比优化写入时的切块方式更有效。 | AgentRunbook-C 在 LongMemEval-V2 上超过了 RAG 基线。 |
| **代价** | 放入上下文的 token 数会增加。 | 查询更慢，有些问题需要遍历整批文件，不能靠一次最近邻搜索解决。 |

索引来自第 4 章的分类记录，记录在写入时已经标明范围，因此每个通道都只查询允许读取的数据。索引维护沿用第 7 章的安排，放在写入流程中；查询本身只读不写。索引损坏后，可以重新处理原始事件来恢复。

融合后的命中结果会交给第 9 章组装上下文。传递的不只是正文，还包括类型、分数、记录时间和来源事件 ID，方便下一步判断怎样使用。

### 比基础流程多了什么

以前一次检索只走一种方式，具体用哪种取决于触发入口。现在，各通道可以一起工作，即使排名不同，也能统一合并。新增通道只需再提供一份有序结果，不必重新设计整个检索流程。

## 各系统的做法

| | Graphiti | MemMachine |
| --- | --- | --- |
| **优点** | 关系和时间查询可在一次搜索中完成，搜索过程不需要调用大语言模型。 | 命中内容会连同所在对话的上下文一起返回。 |
| **局限** | 需要抽取实体，并让图存储与数据保持同步。 | 展开上下文会增加 token 用量，也需要持续保留完整对话。 |
| **设计考虑** | “谁对谁做了什么、何时发生”需要关系信息，仅靠最近邻搜索难以回答。 | 答案可能分散在命中内容的前后，不一定恰好位于同一个文本块里。 |
| **检索通道** | 融合向量相似度、关键词和图遍历。 | 查询用户画像，并搜索完整的对话历史。 |
| **时间处理** | 关系带有时间信息，可以筛选指定时刻仍有效的事实。 | 对话经历本身保留时间顺序，按顺序展开上下文。 |
| **排序与结果调整** | 融合并行搜索得到的排名。 | 重点调整检索深度和结果呈现方式，而非写入时的切块技巧。 |

## 常见问题

- **某个通道返回太多结果。** 它可能对融合结果产生过大影响。RRF 按名次而非原始分数计算贡献，再配合较小且一致的每通道 `k` 值，可以限制这种影响。
- **所有通道都漏掉同一条事实。** 数据存在，却没有合适的检索信号。此时更应该补充时间或实体等新通道，而不是反复调整现有通道的参数。
- **索引与记录不一致。** 删除或数据结构变化可能留下本不该存在的索引项。有疑问时可以从记录重建，索引本来就应当容易重新生成。
- **增大 k 后精度下降。** 候选越多，下游可能接收到越多噪声。融合时保持较小的 k，再由第 9 章按 token 预算进一步筛选。
- **多个通道累加等待时间。** 需要并行的通道应真正并行执行，每条轻量通道尽量只做一次索引查询。展开上下文、自主文件搜索等较慢的工作，应先判断是否需要，再执行。

[`src/`](src/) 在第 7 章的基础上增加：

- [`retrieve.py`](src/retrieve.py)：RRF 融合函数 `fuse`，以及组合各个通道的 `retrieve`。索引本身的实现见[第 7 章：索引与视图](../07-index-views/README.zh-CN.md)。

```bash
python sections/08-hybrid-retrieval/src/test.py   # offline checks, no key
```

离线版使用关键词和最近优先两个通道。接入真实系统时，向量和图检索也可以把结果交给同一个 `fuse`。

## 参考来源

- [Graphiti / Zep](https://arxiv.org/abs/2501.13956)：增量更新的时间知识图谱，融合搜索不调用大语言模型。
- [MemMachine](https://arxiv.org/abs/2604.04853)：重视检索深度和来源上下文，比单纯调整写入切块更有效。
- [HippoRAG](https://arxiv.org/abs/2405.14831)：通过个性化 PageRank，一次检索收集需要关联多条记忆的证据。
- [LongMemEval-V2 / AgentRunbook-C](https://arxiv.org/abs/2605.12493)：让 agent 自行搜索文件，作为较慢但能深入查找的检索通道。
