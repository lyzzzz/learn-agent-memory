# 10 · 评估与管理（Evaluation and governance）

[English](README.md) · [繁體中文](README.zh-TW.md) · **简体中文**

> 要评估效果，先留下记录；指标超出要求时，还要明确接下来怎么处理。

这是[生产环境中的记忆系统](../../README.zh-CN.md)教程的最后一章，负责反馈与评估。前九章已经实现写入、冲突处理、合并整理、索引、排序和上下文组装，现在需要知道这些环节到底做得怎么样，再根据结果调整系统。

记忆系统的问题往往不容易及时发现。审核规则不加筛选地保存所有内容，或者拒绝所有内容，从程序运行状态看都可能没有异常。检索结果也可能看起来合理，实际却是错的。直到回答出错，才发现没有足够的记录可以定位原因。

而且，记忆会随着运行不断变化：记录越来越多，事实逐渐过期，反复整理可能改变原意，索引也可能落后于实际记录。不持续评估，系统就可能在不知不觉中变差，最后由用户发现问题。

---

## 实现机制

最小实现只增加两种事件类型，评估时再从已有日志计算指标，并为每个阈值规定处理动作，不另建一套存储。

评估模块本身不保存新的数据副本。它读取第 2 章的事件日志和记忆记录，现场计算结果。这与第 7 章的视图原则一致：计算结果丢了，可以重新算。核心接口也不变，仍然只有 `observe`、`consolidate`、`recall` 三个方法。

### 增加两种事件

```text
recall  → memory_injected   放入了哪些记忆、用了多少 token、哪些存在冲突
answer  → memory_outcome    哪些记忆有用、哪些造成误导、用户是否更正了答案
              ↓
          写入原有事件日志，只追加，不另建评估存储
              ↓
          读取时计算：写入 · 检索 · 上下文 · 端到端效果
              ↓
          检查阈值，并指出需要采取的处理动作
```

记录回答结果（outcome）不需要给核心接口增加第四个方法。它本身就是对这一轮交互的观察，可以和其他事件一样，通过 `observe` 写入日志：

```python
@dataclass(frozen=True)
class Outcome:
    query: str
    injected: tuple = ()
    used: tuple = ()          # 答案真的有靠的那几笔
    misled: tuple = ()        # 靠了、结果答错的那几笔
    abstained: bool = False   # 答案有没有选择不靠 memory
    corrected: bool = False   # 用户有没有把结果改掉
```

`used` 表示回答实际采用了哪些记忆，`misled` 表示哪些记忆误导了回答。这些标签需要由评估模块之外的信号提供。实际系统通常会让模型在回答时列出使用的记忆 ID，也会根据用户的更正标记误导项。

本章的评估代码不会自行阅读答案，再猜测哪些记忆有用。否则，评估器就可能同时决定答案是否正确，难以得到可靠的分数。

整个流程是：`recall` 在返回记忆区块前，记录选中的内容；调用方拿到答案后，回报结果；`evaluate` 读取这两类事件和记忆记录，计算四层指标，并列出当前未达到要求的检查项。

### 四层指标

下面是 `evaluate` 输出的指标。每个指标都依赖前面章节已经保存的信息，在需要评估时计算：

| 层次 | 指标 | 衡量什么 | 数据来源 | 说明 |
| --- | --- | --- | --- | --- |
| 写入 | 决策数、保存比例、重复率、待审批队列 | 审核做了哪些决定，还有多少内容在等待审批 | 第 3 章的决策记录，包括触发决定的规则 | |
| | 写入精确率（write precision） | 已保存且得到反馈的记忆中，确认保存正确的比例 | 决策记录与回答结果 | 只统计已有判断的记忆；尚未使用的内容不计入，避免把提前保存有用信息算作错误 |
| | 缺少有效来源的记忆比例（unsupported memory rate） | 有多少记忆引用了日志中不存在的事件 | 第 4 章保存的来源事件 ID | 不等于答案中的无依据说法（unsupported claims），后者不在本章评估范围内 |
| | 错误更新率（wrong update rate） | 保存错误、后来被撤回的记忆比例 | 第 5 章的撤回与替换记录 | |
| | 整理方案通过率（consolidation precision） | 提出的整理方案中，有多少没有被验证器拒绝 | 第 6 章报告的拒绝结果 | |
| 检索 | 证据精确率、误导率（evidence precision、misled rate） | 找出的记忆有多少帮上忙、有多少误导了回答 | 实际回答的结果反馈 | |
| | 冲突覆盖率（contradiction coverage） | 发生冲突时，双方信息是否一起进入上下文 | 第 9 章形成的冲突组 | 由于整组选取，单轮只会是 1.0 或 0.0；跨轮平均低于 1.0，说明有轮次丢掉了整个冲突组，回答时双方证据都不在 |
| | recall@k | 应当找回的记忆中，有多少进入前 k 个结果 | 标注数据集 | 没有标注数据，就无法计算 |
| 上下文 | 注入 token 数、每轮注入条数 | 记忆占用了多少提示词空间 | 第 9 章的注入记录 | |
| | 可疑指令命中率（injection hit rate） | 放入上下文的记忆中，有多少看起来像指令 | 注入时记录的检测结果 | 命中不代表攻击成功；区块已标为参考数据，但写入审核仍漏过了应当人工检查的内容 |
| | 未注入比例（no inject rate） | 有多少轮没有放入任何记忆 | 空的注入记录 | |
| | 过期率（stale rate） | 注入时已经失效的记忆比例 | 第 5 章的 `superseded_at`，通过 `as_of` 查询 | 失效时保留了时间戳和原记录，因此事后仍可核查 |
| 端到端 | 轮次数、更正率、未采用记忆的比例（turns、correction rate、abstention rate） | 交互有多少轮、多少答案被更正、多少答案没有依赖记忆 | 回答结果反馈 | |

### 本章暂不评估的内容

有些指标需要额外的数据或判断，本章没有提供这些条件，因此不计算：

| 不计算的内容 | 缺少的条件 |
| --- | --- |
| 时间判断是否正确、答案是否有无依据的说法（temporal correctness、unsupported claims） | 需要评判答案本身，而不仅是检查记忆记录 |
| LongMemEval 的端到端任务分类评分 | 需要标注语料；本章的 `Case` 只有查询和应返回的 ID |
| LongMemEval-V2 的 agent 经验任务分类评分 | 同样需要对应语料，本章只介绍类别，没有附数据 |

这些类别由基准本身定义。LongMemEval 包括信息提取、跨会话推理、时间推理和知识更新，另有后面讨论的不作答能力；LongMemEval-V2 包括静态状态、动态状态、工作流程知识、环境中的易错点，以及前提识别能力（premise awareness）。

### 区分“没放入记忆”和“没采用记忆”

abstention 经常被用来描述两件不同的事，这里分成两个指标：

| | `no_inject_rate` | `abstention_rate` |
| --- | --- | --- |
| **实际发生了什么** | 这一轮没有向上下文放入记忆。 | 回答时决定不依赖记忆。 |
| **反映哪个环节** | 检索和组装阶段的选择：没有值得占用预算的内容，可以是正常结果。 | 回答阶段的判断，由调用方和其他结果一起回报。 |

即使没有注入任何记忆，也要留下记录。否则，日志无法区分“运行过检索，决定不注入”和“根本没有运行检索”。

### 没有数据时，不要返回零

分母为零时返回 `None`，而不是 `0.0`：

```python
def _share(part, whole):
    return part / whole if whole else None
```

“没有测量结果”和“测得结果为零”是两回事。如果把缺失数据也显示成零，一条停止回报结果的流程就可能显示为错误率全为零，让人误以为运行良好。

`recall@k` 也一样：没有标注数据，就没有这个指标；再多的实际流量也不能替代标注，更不能把缺失结果当成满分。

### 给指标设置阈值和处理动作

管理规则体现在 `Gate` 的 `action` 字段中：指标不达标时，必须知道该做什么。仅仅把数字展示在面板上，无法保证有人处理，也无法决定是否应暂停上线。

```python
@dataclass(frozen=True)
class Gate:
    metric: str          # "layer.name"
    limit: float
    action: str          # 踩到的时候要做什么
    floor: bool = False  # 这个 limit 是下限，不是上限

GATES = (
    Gate("write.unsupported_rate", 0.0,
         "block the write path: a memory is citing evidence the ledger does not have"),
    Gate("context.stale_rate", 0.05,
         "reindex after consolidation before serving: closed records are reaching prompts"),
    Gate("context.injection_hit_rate", 0.0,
         "review the write gate: instruction-shaped memories are reaching the prompt"),
    Gate("retrieval.misled_rate", 0.20,
         "hold the learned write policy: these outcomes are too noisy to train on"),
    Gate("retrieval.contradiction_coverage", 1.0,
         "raise the budget or the retrieval cap: conflicts are being dropped whole",
         floor=True),
)
```

如果检查项引用了一个不存在的指标，代码会直接报错。指标名拼错后若只返回“没有数据”，这条检查就可能永远不再触发。明确报错才能避免这种失效被掩盖。

其中，误导率检查体现了“先评估，再信任”的原则。学习型写入策略会使用回答结果来训练；如果这些反馈每五次就有一次是错的，训练也可能把噪声学进去，让系统进一步变差。因此，升级记忆系统自身的策略之前，也要先评估反馈质量。

### 发现错误后，怎样修正

评估发现问题后，需要有对应的处理方式。如果反馈指出某条记忆误导了答案，就可以使用第 5 章已有的 `retract` 撤回操作，不必新增一种核心接口。

撤回后，记录会标为错误，但仍可读取。这里仍要区分：`retracted` 表示内容原本就不成立，`superseded` 表示过去成立、后来情况变了。

撤回是本章唯一改变记忆状态的操作。如果没有任何流程实际调用它，统计撤回的指标就会一直为零，无法反映问题。

### 查询时只追加一条记录

指标计算和阈值检查都放在后台，可以选取需要的时间范围计算，结果丢失后也能重新生成。

查询路径只增加一项工作：每次 `recall` 返回前，追加一条注入记录。这是一次直接写入，不需要先查询其他数据。上下文层的指标都依赖这条记录；少记一次，就有一轮交互无法完整评估。

### 本章增加了什么

与第 9 章相比，`assemble` 现在同时返回选中的记忆和生成的文字区块。引擎因此可以直接记录 ID 和 token 用量，不需要重新执行一次选择过程。

写入决定除了动作，还会用单独的字段记录“由哪条规则做出决定”。指标不再解析日志消息的文字前缀，否则仅仅改一句提示语，就可能让统计失效。

两种事件也分别通过统一的函数写入、读取。计算指标时使用明确的数据类型，不在各处直接按字符串键访问字典。需要统计什么，就把它保存成字段，并通过对应类型读回来。

## 各系统的做法

| | LongMemEval | Memory-R1 |
| --- | --- | --- |
| **优点** | 不同系统可以直接比较，按任务分类的得分也有助于发现哪种能力不足。 | 不依赖人工标注即可改进策略，学习信号来自实际交互结果。 |
| **局限** | 固定数据集可能逐渐过时，通过测试不代表实际运行不会出问题。 | 奖励只看最终答案；错误记忆如果碰巧得到正确答案，也可能被强化。 |
| **设计考虑** | 不同记忆能力应分别评估。 | 以答案是否正确作为最终反馈。 |
| **信号来源** | 标注过的会话及对应证据，按任务类别评分。 | 根据执行结束后的答案正确性，奖励保存、修改、遗忘等动作。 |
| **执行时机** | 离线运行固定数据集，通常在上线前检查。 | 随实际结果持续获得反馈。 |
| **覆盖范围** | 覆盖基准定义的任务类别。 | 取决于实际交互涉及哪些情况，未遇到的情况无法得到训练。 |

## 常见问题

- **有指标，没有处理动作。** 数字展示出来后，如果无人负责，也不影响上线决定，就很难发挥作用。每条阈值规则都应注明触发后怎么处理。
- **让系统自行判定自己是否正确。** 生成答案的模型同时负责判断记忆有没有帮助，评估可能不可靠。应使用外部提供的标签，例如用户更正、模型明确列出的引用 ID，以及人工审核过的数据集。
- **把缺失数据当成零。** 流程停止回报结果后，更正率可能看起来反而更低。应从计算逻辑中区分缺失与零值，不能只在展示层修饰。
- **只看最终总分。** 总分可能受多个环节影响，无法定位原因。按层评估，才能把异常对应到具体阶段。
- **统计一种从不会被记录的事件。** 如果没有代码产生某类记录，对应比率的分子就永远为零，看起来与“没有问题”一样。每个指标依赖的事件，都必须有实际产生和记录的流程。
- **在查询时计算评估结果。** 这会增加用户等待，却往往只是得到稍后才会查看的分数。查询时只记录事件，计算放到后台。
- **一个术语指两件事。** 把“没有注入记忆”和“回答没有采用记忆”都叫 abstention，会混淆检索与推理的表现。应拆开命名、分别统计。
- **通过基准后就停止检查。** 固定数据集只能验证一部分能力。实际运行中的证据精确率和过期率，仍需持续跟踪。
- **审批队列无人处理。** 待审内容不断积压，最终效果就和忽略这类记忆差不多。除了统计审批决定数，还要跟踪队列长度。
- **没有预留合法删除的流程。** 只追加的系统仍可能遇到法律要求的删除。应提供范围明确、可审计、会留下操作记录的专用流程，而不是允许所有模块随意调用 `DELETE`。

## 可运行的代码

[`src/`](src/) 在第 9 章的基础上增加：

- [`evaluate.py`](src/evaluate.py)：`Outcome`、`Injection`、`Case`、`Gate`、四层指标函数、`report` 和 `failing`。两种事件分别有统一的写入与读取函数，指标不直接按字符串键读取字典；缺失结果返回 `None`。
- [`engine.py`](src/engine.py)：`recall` 记录每轮注入，包括空结果；`feedback` 把回答结果作为观察写入；`last_injected` 告知调用方需要回报哪些记忆；`retract` 标记错误记录；`evaluate` 从记录计算整条流程的指标。
- [`policy.py`](src/policy.py)：在统一位置为决定填写触发规则。重复率因此按规则类别统计，不再匹配理由文字。
- [`assemble.py`](src/assemble.py)：同时返回文字区块和选中内容。是否生成区块、怎样估算 token，都沿用选择阶段的同一套逻辑。
- [`test.py`](src/test.py)：检查缺失数据与零值的区别、按动作和规则统计决定、只评估已有反馈的写入，以及来源缺失和注入成本。
  还会验证未注入与未采用两类指标能否区分、预算不足而丢弃冲突组时覆盖率是否下降、撤回后错误更新率是否变化，以及更正前后的过期率。
  最后检查可疑指令是否触发相应规则、不存在的指标是否报错、`recall@k` 是否需要标注数据，以及各条阈值规则是否生效。

```bash
python sections/10-evaluation-governance/src/test.py   # offline checks, no key
```

本章不调用模型，因此没有 `demo.py`。
