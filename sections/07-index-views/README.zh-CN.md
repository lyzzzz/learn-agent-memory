# 7 · 索引与视图（Index views）

[English](README.md) · [繁體中文](README.zh-TW.md) · **简体中文**

> 索引用来帮助读取记忆，不是记忆的唯一来源。索引出错时，可以从原始记录重新生成。

这是[生产环境中的记忆系统](../../README.zh-CN.md)教程的第七章，讨论索引。这里的“视图”指根据已有记录整理出的读取结构：搜索索引、展示当前状态的用户画像、相互链接的 wiki 页面，都属于视图。它们最终都来自同一份原始事件日志。

到这一章，记忆已经有了分类、时间信息和整理历史，但它们还只是一条条记录。不同的问题，需要不同形式的结果：

- “关于部署，我知道什么？”需要按相关程度排列的搜索结果。
- “上周改了什么？”需要按时间范围查记录。
- “这个用户是谁？”通常直接读取当前画像就够了。
- “这些事实之间有什么联系？”更适合通过互相链接的页面来查看。

每种查询都需要合适的数据结构。全部挤进同一个索引，既可能变慢，也容易返回不合适的结果。

## 实现机制

最小实现保留一条写入流程，再根据读取需求生成多种视图。原始事件日志始终是最终的数据依据：

```text
原始事件日志    SQLite，只追加；保留原始数据，不靠重建生成
  → 记忆记录    分类、处理冲突、合并整理（第 4—6 章）
    → 稀疏索引  FTS5 / bm25              精确查找名称、日期等信息
    → 时间视图  按 recorded_at 筛选      查看某段时间内的变化
    → 用户画像  每个主张键对应一项        直接读取当前状态，不必搜索
```

生产系统还可能增加向量视图（embedding）、wiki、实体关系图，以及保存技能和操作手册的流程视图。无论有多少种，数据都从事件日志流向视图，不能反过来把视图当成原始依据。

因此，索引出错时可以直接重建：

```python
def rebuild(self, scope, records) -> int:
    con.execute(f"DELETE FROM memory_index WHERE {_SCOPE}", _args(scope))
    con.executemany("INSERT INTO memory_index VALUES (?, ?, ?, ?, ?, ?)", ...)
```

重建会先删除、再插入，删除范围由 `scope` 决定。如果表里没有归属字段，为一个租户重建时就可能清空整张表，然后只写回这个租户的数据，其他租户的索引就丢了。

第 8 章会在每次写入完成后触发重建。缺少范围限制时，最后写入的租户会覆盖其他人的索引，而且其他租户只会得到空结果，不一定收到报错。因此，索引的每次读取和重建，都必须和原始日志一样按范围操作。

数据结构变了、索引损坏了、分词器换了，都可以再次调用 `rebuild`。索引中的每一行都能从记忆记录重新生成，不必逐条修补。

也不是所有视图都需要持久保存。搜索需要倒排索引，这里的稀疏索引和时间视图保存在 SQLite 中；用户画像通常很小，可以读取时直接计算，避免多维护一份容易过期的数据：

```python
def profile(records) -> dict:
    """Current state, one entry per claim key, newest wins."""
```

第 5 章的主张键在这里再次发挥作用：它标识同一个会随时间更新的事实。用户画像按键整理当前状态；没有这个键，就只能列出最近几条记忆，无法得到真正的当前画像。

本章提供 `reindex` 方法，用某个范围内仍有效的记录重建稀疏索引，但还没有自动触发它。第 8 章会在修改记录后自动重建对应范围，检索只读取已建好的索引。

这也对应三种处理时机：

- **查询时：** 只读取索引，不重建。
- **写入后：** 维护索引。教学实现会重建整个范围；生产系统通常只新增或删除受影响的行，让成本取决于改动量。
- **后台：** 数据结构、分词器变化或索引损坏时，做完整重建。

无论在哪个阶段维护，持久索引都不可省略，因为 BM25 排序需要倒排索引提供的数据。本章不调用模型，也不负责决定最终哪些结果最相关。

### 其他常见视图

wiki 和图是经常被讨论的两种组织方式：

| | wiki 视图 | 图视图 |
| --- | --- | --- |
| **数据形式** | 相互链接的 Markdown 页面，每个主题一页。 | 实体作为节点，带类型的关系作为边。 |
| **适用前提** | 以 Markdown 为主要维护形式，人和 agent 都通过普通文件工具编辑页面。 | 关联查询和多跳问题足够多，值得承担抽取关系的成本。 |
| **如何建立链接** | 编辑页面时，把链接写进正文。 | 从每条事件中抽取关系，生成图中的边。 |
| **适合的用途** | agent 自主研究、人工审查、浏览资料。 | 查询关系和时间，一次找齐跨多层关系的证据。 |
| **常见问题** | 没有维护链接时，各页互不相连。 | 关系抽取错误时，遍历结果也会出错。 |
| **代表系统** | [Karpathy 的 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)、Claude Code 自动记忆。 | [HippoRAG](https://arxiv.org/abs/2405.14831)、[Graphiti](https://arxiv.org/abs/2501.13956)。 |

本章的示例不满足这两种方式的适用前提，因此没有实现它们。

### 本章增加了什么

第 6 章之后，系统已有可用的记忆记录。本章为这些记录建立不同的查询通道，第 8 章再负责合并通道结果、统一排序。

建索引和检索排序分开实现，也能分开排查问题。否则，排序有误时，很容易误以为索引本身出了问题。

## 各系统的做法

| | Claude Code 自动记忆 | HippoRAG |
| --- | --- | --- |
| **优点** | 不需要额外搭建基础设施，人可以直接查看和编辑文件。 | 多跳问题可以一次检索完成，减少反复查询。 |
| **局限** | 检索依赖文件工具，目录变大后可能难以找全内容。 | 需要维护抽取流程和关系图，错误关系会影响遍历。 |
| **设计考虑** | 用户能看到记忆内容，才方便检查和修正。 | 需要关联多条事实的答案，尽量不依赖多轮检索。 |
| **记录单位** | Markdown 文件，以及列出这些文件的索引文件。 | 从文本段落中抽取的实体节点和关系边。 |
| **链接方式** | 正文中的 Markdown 链接。 | 使用带类型的关系边，从问题中的实体出发运行个性化 PageRank。 |
| **重建方式** | 重新生成文件；目录较小时，全量重写的成本不高。 | 重新处理整份语料，抽取关系并建立索引。 |

## 常见问题

- **只把信息写进索引。** 没有原始事件作为依据的信息，会在重建时丢失。每个视图都应来自记忆记录，记忆记录又来自事件日志；重建丢数据，说明写入流程有问题。
- **视图没有及时更新。** 记忆已经失效，索引却仍然返回它。每次修改记录后都要更新索引，不能只依赖定时任务。
- **所有视图都持久保存。** 保存的副本越多，越容易出现过期和不一致。搜索需要的结构应保存，小型视图可以读取时计算。
- **共用索引却没有范围字段。** 查询可能返回其他租户看似相关的数据，重建也可能误删别人的索引。应在数据结构中保存范围，并在每次读取时过滤。
- **wiki 链接无人维护。** 没有链接，页面就只是分散的记录；链接指向失效内容，又会让 agent 查到空结果。实现这种视图时，需要负责生成链接，并确保它们指向有效记录。
- **建图却没有相应的查询需求。** 每条事件都要付出关系抽取和建索引的成本。如果不需要多跳查询，效果可能与 wiki 相近，成本却高很多。
- **在索引层决定最终相关性。** 每个通道负责返回候选结果，跨通道融合排序由第 8 章处理。职责混在一起，两部分就难以独立验证。

## 可运行的代码

[`src/`](src/) 在第 6 章的基础上增加：

- [`index.py`](src/index.py)：`MemoryIndex` 提供 `rebuild`、`keyword`、`recent`、`between`、`count`，每个方法都接收范围参数；另有读取时计算的 `profile`。
- [`engine.py`](src/engine.py)：`reindex` 重建指定范围的稀疏索引，`between` 按时间段读取，`profile` 用同一批记录生成用户画像。
- [`test.py`](src/test.py)：检查关键词和时间查询、清空后能否完整重建、画像是否按主张键整理并排除失效记录，以及其他租户能否读到本租户重建的索引数据。

```bash
python sections/07-index-views/src/test.py   # offline checks, no key
```

本章不调用模型，因此没有 `demo.py`。
