# 6 · 合并与整理（Consolidation）

[English](README.md) · [繁體中文](README.zh-TW.md) · **简体中文**

> 模型可以建议合并哪些记忆，但不能自行删除原始证据。

这是[生产环境中的记忆系统](../../README.zh-CN.md)教程的第六章，讨论怎样把积累的事件整理成可用的知识。

合并整理（consolidation）要做的事情比写摘要多得多：去除重复，识别同一个实体，发现矛盾，标记过期信息，合并相关事实，从多次经历中归纳偏好，从成功的执行中整理工作流程，更新置信度，以及淘汰不再有用的记忆。

第 5 章只处理了其中一种情况：用新信息替换旧信息。本章继续处理其他整理工作，也是第一次让模型参与决定怎样处理已经保存的记忆。

风险也在这里。此前主要是新增记录，旧记录的失效由明确的冲突规则处理。现在，模型会提出让哪些记录失效的建议。它可能判断错误，受到提示词注入影响，也可能分不清两条相似记忆中哪条更重要。

## 实现机制

最小实现把“提出方案”和“执行方案”分开：提议器（proposer）给出整理方案，验证器检查，只有通过的方案才会修改存储。

```text
提议器：模型或规则
    ↓ Proposal：整理方案
check()   检查层级、类型、内容、来源数量、来源是否存在、
          来源是否仍有效、是否属于同一范围、主张键是否一致
    ↓
apply()   写入新记录，再让方案引用的旧记录失效
    ↓
操作列表 → 写回事件日志
```

整理工作分为三个层级，越往下，越需要从原始材料中做出新的判断：

```text
compression   压缩：多条相似记忆 → 一条更简短的记忆
abstraction   归纳：多次经历     → 一条规则或偏好
skill         技能：多次成功执行 → 一个可重复使用的操作流程
```

压缩主要是改写，不应加入来源中没有的信息。归纳则会从个别情况得出一般结论，因此更容易过度概括。比如，五次经历都只是某一个测试不稳定，最后却归纳成“整套测试都不可信”。

整理成技能最有价值，风险也最高：前三次成功可能只是碰巧条件合适，但整理后的流程未必保留这些限制，第四次仍可能直接被采用。

一份 `Proposal` 只描述两件事：新内容是什么，要替换哪些旧记录。它不能自由指定操作类型。模型如果想让旧记录失效，就必须提出替代内容，无法只提出删除：

```python
@dataclass(frozen=True)
class Proposal:
    level: str
    content: str
    source_ids: tuple
    kind: str = "semantic"
    reason: str = ""
```

`check` 是方案执行前的验证器，使用固定规则检查八类问题：不支持的层级、不支持的类型、空内容、来源少于两条、来源不存在、来源已经失效、来源跨越多个归属范围，以及来源的主张键不一致。

创建记录时可能失败的条件，也要在这里提前检查，因为后面的 `apply` 会修改存储。执行到一半才失败，会让记录与事件日志不一致，也不利于恢复。被拒绝的方案必须连同原因一起报告，第 10 章会用这些信息评估整理效果。

另外，旧记录失效后，它引用的证据必须完整保留。每条记忆都保存着来源事件 ID；`apply` 只让方案指定的旧记忆失效，并把这些记忆引用的所有事件 ID 合并到新记录中：

```python
events = tuple(sorted({e for r in sources for e in r.source_event_ids}))
derived = make_record(sources[0].scope, proposal.kind, "inference",
                      proposal.content, events,
                      min(r.confidence for r in sources),
                      tags=("consolidated", proposal.level),
                      claim_key=one_key(sources),      # 不带的话 profile view 会变空
                      valid_from=at)                   # 不填的话它会变成「一直都成立」
```

这段代码有三点需要留意。第一，新内容标为 `inference`，因为它是系统整理出的推论，不是直接观察到的事实。第二，置信度取来源中的最小值，不取平均值：合并不会自动让原本不确定的内容变得更可靠。第三，来源事件 ID 始终指向原始日志，保证新记录仍能追溯到最初的观察。

每次运行 `consolidate`，都会报告提出了多少方案、执行了多少，以及哪些方案被拒绝：

```python
return {"proposed": len(proposals), "applied": len(proposals) - len(rejected),
        "rejected": rejected, "operations": ops}
```

完整流程是：引擎读取当前范围内仍有效的记忆，交给提议器；验证返回的方案，执行通过的部分；最后把操作和被拒绝的方案都写回事件日志。

这些工作不需要在用户等待回答时完成，可以定时执行，也可以利用两次会话之间的空闲时间。这样，即使整理需要多花几秒调用模型，也不会增加当前这一轮的响应时间。[Sleep-time Compute](https://arxiv.org/html/2504.13171v1) 讨论的正是这种安排。

### 接入前面代码时发现的两个问题

下面两个问题同样是在接入整条流程后才暴露出来的。修正保留在本章代码中，前面的章节继续保留当时的版本，便于对比。

**问题一：暂缓处理的内容没有被保存。** 写入审核会把相似的候选记忆标为 `DEFER`，理由是“已有相似记忆，交给后续整理阶段合并”。但原来的实现并没有保存这些候选内容，整理阶段自然也就读不到它们。

修正放在引擎的写入流程中：`DEFER` 的候选内容也要存下来，并加上 `deferred` 标签。这样，落在“相似、需要合并”这个区间的记忆，才能真正进入后续处理：

```python
if decision.action in (STORE, DEFER):
    # DEFER 的意思是「交给 consolidation 合并」，
    # 所以 candidate 得活到第 6 章看得到它
    record = make_record(scope, candidate.kind, epistemic_type,
                         candidate.content, candidate.source_event_ids,
                         decision.confidence, claim_key=candidate.claim_key,
                         tags=("deferred",) if decision.action == DEFER else ())
```

如果没有地方保存待处理内容，“暂缓”实际上就等于忽略，只是记录的理由不同。

**问题二：两边计算相似度的方法不同。** 保存下来还不够。写入审核使用一种算法，整理时分组却使用另一种。同一对记录可能在审核时被判为足够相似，进入待合并状态，到整理时却又达不到合并阈值，结果一直留在存储中无人处理。

解决办法是共用同一个相似度函数和阈值：

```python
from policy import SIMILAR_AT, resembles

MERGE_AT = SIMILAR_AT          # gate 用多少延后，这里就用多少合并

# propose_compression 分组时：
resembles(record.content, r.content) >= MERGE_AT
```

两个阶段必须对“多像才需要合并”使用同一套标准，交接才有效。

## 各系统的做法

| | A-Mem | Sleep-time Compute |
| --- | --- | --- |
| **优点** | 新知识可以立即使用，通过笔记链接查找相关内容，不需要另建图存储。 | 整理成本不影响当前对话的响应时间，因此可以承担更复杂的处理。 |
| **局限** | 每次写入都要付出整理成本；错误链接可能被后续笔记继续引用。 | 两次后台处理之间，知识可能仍是旧的；新的更正要到下一次处理后才生效。 |
| **设计考虑** | 记忆应随着新内容加入而重新组织，类似卡片盒笔记法（Zettelkasten）。 | 当前回答用不到的计算，可以放到当前交互之外完成。 |
| **触发时机** | 写入新笔记时，连接相关旧笔记，并修订它们。 | 定时执行，或在会话间隙运行。 |
| **产出** | 相互连接的笔记，旧内容会随新信息更新。 | 预先整理好的上下文，在问题到来之前准备好。 |
| **成本安排** | 每次写入都产生开销，计入交互延迟。 | 批量处理，放在查询流程之外。 |

## 常见问题

- **合并时丢掉唯一证据。** 旧记忆失效后，如果新记忆没有保留来源，就无法核查。新记录应引用所有来源事件 ID 的并集，原始日志也继续保留。即使一次整理出错，仍能重新处理原始事件来恢复。
- **少数例外被删掉了。** 例如四条记录说部署正常，一条说周五部署会失败。压缩时只保留多数说法，就丢了关键例外。合并前必须确认内容是否一致，不能只看文字相似度。
- **整理拖慢查询。** 在检索中途插入模型调用，会让每轮对话多等几秒。整理应定时执行或放在会话间隙。
- **把整理结果标成事实。** 整理后的内容是推论。标成 `fact` 后，它可能在检索中获得比原始观察更高的可信度。
- **反复整理导致意思变化。** 已合并的内容继续被改写，小偏差会逐次积累。每次只处理仍有效的记录；对于已经稳定的记忆库，再运行一次时不应继续提出整理方案。
- **看不到被拒绝的方案。** 验证器如果只丢弃错误方案，就会掩盖提议器的问题。拒绝原因应报告出来，并写入事件日志。
- **跨范围合并。** 两个租户可能用相同文字描述偏好，但不能合成一条记忆。来源不属于同一范围时，验证器必须拒绝方案。
